# Mindsphere

Каталог программ мероприятий DI EVENT и рабочий раздел сотрудников на Django.

## Возможности

- Посетители без регистрации просматривают публичный каталог из 21 программы. При ширине окна от 1024px каталог основан на макете PDF; на более узких экранах телефонов и планшетов используется адаптивная вертикальная вёрстка. Оглавление ведёт к программам на той же странице.
- Сотрудники после входа открывают отдельные карточки с полным внутренним описанием, создают, редактируют и удаляют программы, меняют пароль.
- Учётные записи создаёт администратор. Самостоятельной регистрации нет. Вход доступен по прямой ссылке `/auth/login/`; гостевой каталог её не показывает.

## Технологии

Python **3.12**, Django **6.1.3**, SQLite, Pillow, sorl-thumbnail, django-cleanup и pytils. Локальное окружение проверено на Python 3.12.12 / macOS.

Используется один `requirements.txt` с точными версиями. Комментарии разделяют пакеты приложения, инструменты разработки и транзитивные зависимости. Установка этого файла также устанавливает pytest, flake8, Debug Toolbar и django-extensions.

## Структура

```text
requirements.txt           # все зависимости
.env.example               # образец серверных переменных без секрета
.htaccess                  # запуск Python через Passenger на Beget
passenger_wsgi.py          # серверная точка входа, config.production
AGENTS.md                  # текущее состояние и правила работы с проектом
sphere/
    manage.py
    config/                # настройки и маршруты
    core/                  # общие вспомогательные компоненты
    events/                # модели, формы, каталог, импорт и тесты
    users/                 # вход и работа с учётными записями
    templates/             # HTML и SVG-шаблоны
    static/                # общая исходная статика
    db.sqlite3             # локальная база, не хранится в Git
    media/                 # загруженные файлы и миниатюры, не хранятся в Git
```

Стили, скрипты и ресурсы отдельных приложений находятся также в `sphere/events/static/` и `sphere/users/static/`.

## Установка и локальный запуск

Команды ниже выполняются из корня репозитория на macOS/Linux. Для новой установки нужен Python 3.12:

```bash
python3.12 -m venv venv
venv/bin/python -m pip install -r requirements.txt
venv/bin/python sphere/manage.py migrate
venv/bin/python sphere/manage.py createsuperuser
```

Если рабочее окружение `venv` уже существует, пересоздавать его не требуется. `migrate` создаёт или обновляет схему базы; программы каталога эта команда не загружает. Миграции приложения хранятся в репозитории, включая 0012 и 0013 с публичными полями и настройками публикации.

Запуск сервера разработки:

```bash
venv/bin/python sphere/manage.py runserver
```

| Адрес | Назначение |
| --- | --- |
| `http://127.0.0.1:8000/` | Публичный каталог |
| `http://127.0.0.1:8000/auth/login/` | Вход сотрудников |
| `http://127.0.0.1:8000/admin/` | Администрирование и создание пользователей |
| `/events/<slug>/` | Полная карточка, доступна после входа |
| `/create/` | Добавление программы, доступно после входа |

## Первоначальная загрузка каталога

В репозитории есть исходные данные всех 21 программы, иллюстрации, шрифты и SVG-макеты. Оригинальный PDF для запуска не требуется. Для заполнения новой базы выполните:

```bash
venv/bin/python sphere/manage.py load_pdf_catalog --replace
```

**Повторный запуск перезаписывает публичные поля исходных программ значениями из PDF**, включая тексты, порядок и ссылки на иллюстрации. Флаг `--replace` также снимает остальные программы с публикации. Пользователи, внутренние описания и прежние файлы сохраняются.

Используйте импорт для новой базы или намеренного восстановления исходного каталога. Для переноса уже отредактированного сайта нужны его база и медиафайлы. Импорт не вызывается автоматически при запуске или применении миграций.

## Редактирование и данные

Обе версии каталога используют одну модель `Event`. Название, слоган, краткое описание, состав концепции, формат, тайминг и дресс-код — публичные поля. Полное поле `description` предназначено только для сотрудников и может быть пустым. Оно не подставляется вместо краткого публичного описания.

Программы сортируются по `sort_order`, затем по ID. Флаг `is_published` управляет показом в каталоге. Обычные изменения выполняются через формы сайта или админку и сохраняются в базе. `sphere/events/catalog_source.json` — источник явного импорта, а не замена текущей базы. Поле `catalog_page` связывает исходную программу с её графическим макетом.

Тексты, пользователи и настройки программ хранятся в `sphere/db.sqlite3`, загруженные изображения — в `sphere/media/`. Эти данные исключены из Git. Копия репозитория сама по себе не переносит содержимое работающего сайта. Исходная статика, иллюстрации PDF и шрифты входят в репозиторий.

## Проверки

Из корня репозитория:

```bash
venv/bin/python -m pip check
venv/bin/python sphere/manage.py check
venv/bin/python sphere/manage.py makemigrations --check --dry-run
venv/bin/python sphere/manage.py showmigrations
venv/bin/python sphere/manage.py test events.tests users core.tests
```

Для общего набора Django-тестов и pytest-тестов после установки зависимостей:

```bash
cd sphere
../venv/bin/python -m pytest
```

Тесты используют отдельную тестовую базу. Проверка `makemigrations` выше не создаёт миграций и не применяет их к рабочей базе.

## Развёртывание

### Локальные и серверные настройки

Обычный `manage.py runserver` использует `config.settings`: локальные адреса, `DEBUG=True` и ключ разработки. Серверный `passenger_wsgi.py` выбирает `config.production`: `DEBUG=False`, защищённые cookies и отдельный секрет. Локальный запуск не читает `.env` и не требует серверных переменных.

Общие настройки, `.htaccess`, `passenger_wsgi.py` и `.env.example` хранятся в Git. Реальный `.env`, виртуальное окружение, `public_html`, ссылка `public`, служебная `tmp`, база и `media` исключены из Git. Данные мероприятий и пользователей не синхронизируются через `git pull`.

В корневом `.env` на сервере задаются:

| Переменная | Назначение |
| --- | --- |
| `DJANGO_SECRET_KEY` | Новый случайный секрет. Без него серверный запуск останавливается; ключ разработки не используется как запасной. |
| `DJANGO_ALLOWED_HOSTS` | Домены через запятую, без схемы и пути. В примере — `workspace-test.dievent.ru,workspace.dievent.ru`. Без списка запуск останавливается. |
| `DJANGO_SECURE_SSL_REDIRECT` | `true` или `false`. Изначально `false`, чтобы тестовый публичный каталог оставался доступен по HTTP. |

Поддерживаются строки `KEY=value`, пустые строки, комментарии на отдельных строках и значения в одинарных/двойных кавычках. Подстановка переменных и выполнение команд не поддерживаются. Переменные окружения процесса имеют приоритет над файлом. При необходимости переменная окружения `DJANGO_ENV_FILE` указывает другой путь к файлу.

Файл `.env` должен быть доступен для чтения пользователю Passenger, но не размещаться в `public_html`. Не выводите его содержимое в журнал и не добавляйте в Git. Новый ключ не изменяет пароли, но после его подключения ранее выданные сессии потребуют повторного входа.

### Подготовка Beget

Подтверждён запуск на обычном хостинге Beget через Passenger: Python 3.12.16, Django 6.1.3, OpenSSL 3.5.9, SQLite 3.37.2. Код размещён прямо в `/home/v/v2505714/mindsphere_new`, окружение — в `venv` рядом с `sphere`. В `.htaccess` указан абсолютный путь этого окружения; при смене папки/аккаунта нужно обновить `PassengerPython`. Сам WSGI-файл вычисляет путь к проекту относительно себя.

Локальный macOS-venv на сервер не переносится. Серверные зависимости устанавливаются из единственного `requirements.txt`. Для входа в Docker после SSH-подключения к аккаунту используется `ssh localhost -p222`.

Для новой установки создайте `.env` на основе `.env.example`. Следующий блок выполняется **в корне серверного проекта**, создаёт новый секрет и не перезаписывает существующий файл:

```bash
venv/bin/python - <<'PY'
import os
from pathlib import Path
import secrets

template = Path('.env.example').read_text()
content = template.replace(
    'DJANGO_SECRET_KEY=',
    'DJANGO_SECRET_KEY=' + secrets.token_urlsafe(64),
    1,
)
fd = os.open('.env', os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o640)
with os.fdopen(fd, 'w') as file:
    file.write(content)
print('.env создан; секрет не выведен.')
PY
```

Проверьте разрешённые домены для конкретной установки. Для управления серверным сайтом выбирайте тот же профиль, что и Passenger:

```bash
venv/bin/python sphere/manage.py check --settings=config.production
venv/bin/python sphere/manage.py migrate --plan --settings=config.production
venv/bin/python sphere/manage.py collectstatic --noinput --settings=config.production
```

`check` проверяет конфигурацию. `migrate --plan` показывает ожидаемые миграции, не применяя их. Если база уже перенесена и все миграции применены, заново создавать её не нужно. `collectstatic` собирает ресурсы в `public_html/static`; её повторяют после загрузки изменений статических файлов. База остаётся в `sphere/db.sqlite3`, медиа — в `sphere/media`.

Для нового сайта создаются ссылки `public → public_html` и `public_html/media → ../sphere/media`. Существующие ссылки повторно создавать не требуется. Штатную заглушку `public_html/index.php` переносят в резервную папку за пределами `public_html`, чтобы она не подменяла главную Django. Перезапуск Passenger — `touch tmp/restart.txt` из корня проекта.

Beget изолирует сайты через ACL. Python в `.local` должен быть доступен пользователю сайта: при ошибке `Cannot execute ... python3.12: Permission denied` через файловый менеджер был предоставлен доступ «Чтение», «Включая вложенные папки» к `.local`. Не открывайте общий доступ ко всей домашней папке. Официальная инструкция: [окружение приложений Beget](https://beget.com/ru/kb/how-to/web-apps/obshhie-svedeniya-po-ustanovke-prilozhenij-virtualnoe-okruzhenie-docker).

### HTTPS и обновления

`SESSION_COOKIE_SECURE` и `CSRF_COOKIE_SECURE` включены в серверном профиле. По HTTP можно проверять публичный каталог; вход и отправку форм с реальными данными проверяют по HTTPS. Перенаправление на HTTPS включают после проверки сертификата и того, как Passenger определяет защищённый запрос. Недоверенные proxy-заголовки автоматически не принимаются; HSTS пока не включён. При начальной конфигурации `check --deploy --settings=config.production` поэтому предупреждает об HTTPS redirect и HSTS. Проверка не заменяет фактическую проверку HTTPS.

Сертификат основного `workspace.dievent.ru` уже установлен на Beget. Перепривязка домена к новой папке и проверка HTTPS выполняются отдельно после проверки новой версии; репозиторий сам домены не переключает.

Дальнейший порядок обновления кода: локальные изменения и проверки → commit/push → на сервере `git pull --ff-only` → обновление зависимостей при изменении `requirements.txt` → проверка/применение необходимых миграций → `collectstatic` при изменении статики → перезапуск Passenger. Перед миграциями или заменой данных нужна резервная копия базы и медиа; повторно загружать локальную базу поверх работающей при каждом обновлении не нужно.

**Первый переход с временного запуска:** сейчас на Beget `.htaccess` и `passenger_wsgi.py` созданы вручную и ещё не отслеживаются серверным Git. Новый WSGI выбирает `config.production`, поэтому `.env` должен быть подготовлен до перехода. Перед первым обновлением следует сохранить оба ручных файла вне репозитория и отдельно согласовать их замену версиями из Git: обычный `git pull` может остановиться из-за совпадающих неотслеживаемых файлов. Не обходите это через `git reset --hard`, `git clean` или удаление данных. Эти действия на сервере пока не выполнены.

При первоначальном переносе содержимого отдельно переносятся согласованная копия базы и `media`. Источником старого работающего сайта была MySQL, а оставшийся на нём SQLite-файл оказался устаревшим. Перед заменой данных всегда проверяйте фактическое подключение и содержимое, особенно пользователей и внутренние описания. Команду импорта PDF вместо переноса отредактированной базы не используют.
